## Objective

Verify that when two members change a trip's membership at the same time, no removed member comes back and the trip is never left without an admin. This run covers the sole admin transferring admin status to a member who leaves the trip while the Transfer Admin dialog is open.

## Preconditions

- Two Syncinary accounts exist: Account A and Account B.
- Account A has created a trip and is its only admin.
- Account B has joined the trip as a regular user.
- No other members are in the trip.
- The tester can be signed in to both accounts at once (e.g. a normal and an incognito browser window).

# Bug Report

## Bug Information

| Field | Details |
| --- | --- |
| Bug ID | BUG-002 |
| Title | Trip Left With No Admin After Transferring Admin to a Member Who Already Left |
| Related Test | 401-5 |
| Reported By | Prisha Boreddy |
| Date Reported | 10/11/2026 |
| Severity | High |
| Priority | Medium |
| Status | Open |

## Description

If the trip's only admin opens the Transfer Admin dialog and the member they choose leaves the trip before they confirm, the transfer still goes through. The admin is demoted to a regular user, but nobody is promoted because the chosen member is no longer in the trip. The trip is left with no admin, so nobody can rename it, remove members, transfer admin, or delete it, and the app has no way to recover.

## Environment

| Field | Details |
| --- | --- |
| Platform | Web |
| Browser | Chrome |
| Operating System | Windows |
| Application Version / Branch | main @ 4d715b5 (version 0.3.0+1) |

## Preconditions

- The trip has exactly one admin (Account A) and at least one other member (Account B).
- Account A and Account B are signed in at the same time in separate windows.

## Steps to Reproduce

1. As Account A, open the trip and click "Transfer Admin Status". Leave the dialog open.
2. As Account B, leave the trip from My Groups.
3. As Account A, select Account B in the dialog and click "Confirm Selection".
4. As Account A, look at the trip page.

## Expected Result

The transfer should not happen, because Account B is no longer a member. Account A should remain admin and see a message that the member is no longer in the trip. The trip should never be left without an admin.

## Actual Result

Account A sees "[Account B] is now the admin", but Account A is demoted to a regular user and Account B is not in the trip. The trip has no admin, and the admin-only controls (rename, remove member, Transfer Admin Status, Delete Trip?) are gone for everyone.

This was reproduced with an automated test against a fake Firestore. Confirm it in the app using the steps above.

## Evidence

Automated reproduction (fake Firestore): after removing the member and then calling `transferAdmin` with the stale member, the trip's members were:

```
{me: {username: me, email: , role: user}}
```

The former admin is the only member left, with the role `user`.

## Additional Notes

Suspected cause (from reading the code):

- `transfer_admin_dialog.dart` builds its member list from the group as it was when the dialog opened (`widget.group`), so it can show members who have since left.
- `GroupService.transferAdmin` (`group_service.dart`) demotes the current user unconditionally: `members[currentUserId]?['role'] = 'user'`. It only promotes the new admin if they are still in the trip (`members[newAdmin.id]?['role'] = 'admin'`), so when they're missing, nobody is promoted.

Possible fix: in `transferAdmin`, only demote the current user if the new admin is still a member, and throw (or return false) otherwise so the dialog can show an error. A regression test for the 501-7 row should check that the trip still has exactly one admin in this case.

The same flaw happens with two admins (another admin removes the member while the dialog is open), but there the second admin remains, so the trip still has an admin.
