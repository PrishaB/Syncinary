## Objective

Re-run 401-5 after the BUG-002 fix (#189, merged in PR #214) to verify that when two members change a trip's membership at the same time, no removed member comes back and the trip is never left without an admin. This run covers the sole admin transferring admin status to a member who leaves the trip while the Transfer Admin dialog is open.

## Preconditions

- Two Syncinary accounts exist: Account A and Account B.
- Account A has created a trip and is its only admin.
- Account B has joined the trip as a regular user.
- No other members are in the trip.
- The tester can be signed in to both accounts at once (a normal and an incognito browser window).

# Bug Report

## Bug Information

| Field | Details |

| Related Test | 401-5 |

## Description

On web, if the admin confirms a transfer to a member who has left the trip since the Transfer Admin dialog opened, nothing visible happens. The transfer is correctly refused and no data changes, but the dialog never shows "[member] is no longer in this group. Choose someone else.", so the admin can't tell why. The same applies to the "You're no longer an admin of this group." message.

## Environment

| Field | Details |
| --- | --- |
| Platform | Web |
| Browser | Chrome |
| Operating System | Windows 11 |
| Application Version / Branch | main @ 532d0d8 (version 0.6.0) |

## Preconditions

- The trip has one admin (Account A) and one other member (Account B).
- Both accounts are signed in at the same time in separate windows.

## Steps to Reproduce

1. As Account A, open the trip, click "Transfer Admin Status", and select Account B. Leave the dialog open.
2. As Account B, leave the trip from My Groups.
3. As Account A, click "Confirm Selection".

## Expected Result

The dialog says Account B is no longer in the group, removes them from the list, and Account A stays admin.

## Actual Result

Nothing visible happens. Account A stays admin and Account B is not brought back, but no message appears and the browser console logs an uncaught `RethrownDartError: Dart exception thrown from converted Future`.

## Evidence

See the console output in the 401-5 report above.

## Additional Notes

Cause: `GroupService.transferAdmin` runs inside a Firestore transaction and throws `MemberNotFoundException` (or `NotAdminException`) from inside the transaction handler. On web, `cloud_firestore_web` turns any Dart error thrown inside a transaction into a JavaScript `Error` ("Dart exception thrown from converted Future") and only converts real Firebase errors back into Dart exceptions. The dialog's `on MemberNotFoundException` therefore never matches, and the error goes unhandled.

Fix (branch `transfer_admin_web_error`): `GroupService._updateMembers` catches the exception inside the transaction, ends the transaction without writing, and rethrows the original exception after the transaction finishes. `AccountService` already uses the same pattern. Regression tests: `groups_flow_test.dart` `[501-7] ... (web, BUG-003)`, which run against a fake Firestore that wraps transaction errors the way the web plugin does. Both failed before the fix and pass after it.
